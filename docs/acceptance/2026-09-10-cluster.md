# First-boot acceptance — 2026-09-10, Sam's four-Machine cluster

Release under test: `repo-2026.09.10-2a1a417` (zero, three) and
`repo-2026.09.10-ada52e2` (one, two; the same image plus #235).
Boxes: four ThinkCentre M920q, each with an onboard NIC and an SFP+ card,
on a 10 GbE managed switch. Sticks: four SanDisk 3.2Gen1 57 GB, flashed
from a LOCAL build of the released commit with the operator's ssh key baked
(`AUTH_KEYS=… make usb`, never published — docs/fulfillment.md § Batch prep),
`wipefs -a` first on the three that had carried a Machine before.

## 1. The stick
- [x] Flashed with `scripts/70-flash.sh --image out/pipeos-usb.img /dev/sdX`
      (local build of the released commit; see header for why not the asset).
- [x] After the whole-image dd, `findfs LABEL=PIPEWORK` resolved nothing on
      every stick — `wipefs` on the reused ones was necessary: without it the
      old ext4 superblock survives the dd and `grow.sh` would not carve /work.

## 2. Power to the page
- [x] `http://pipeos-<id>.local/` answered within ~3 min of power-on on all
      four (first boot carves /work and reinstalls packages). Timed from the
      workstation's lobby watch, not a phone; the phone row is still owed.
- [x] With a second Machine up: each new box appeared in the others' lobby
      within 10–20 s of answering, `siblings` counted correctly (3 on each
      at the end).
- [x] Chassis id: every box's id came from eth0 — on these boxes the SFP+
      card (`24:8a:07:…`), which is the cabled port; the onboard `e8:6a:64:…`
      is eth1 and down. Ids matched the ids the same hardware had the day
      before (a4e0, c360), so an id survives a reflash.
