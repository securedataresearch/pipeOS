# SMB acceptance — 2026-09-11, the pilot's share on zero

The pilots (#159) need a network share; this is the first time the flow was
walked on the cluster hardware (#163 was verified on basho_box, since
reflashed). Box: zero (pipeos-a4e0, .77), overlay 15cbc74 (#267 deployed
minutes before). Driven through the dashboard API exactly as the Storage
and Users pages post it — no ssh writes. Client: Sam's workstation,
`smbclient` 4.x over SMB3. Operator: Claude; Sam watching.

## 1. Before: what a client meets
- [x] **Found and fixed (#266/#267)**: the Services toggle had turned network
      storage on with no share; zero booted DEGRADED (`pipeos-nas down`).
      Now declined with a note; selfcheck names the cause.
- [x] **Found (design)**: a share needs an account with unix access, and
      unix access needs an ssh public key *or* a browser terminal. A client
      who wants only a share must therefore also give the account a terminal
      password. Worked, but it is a detour a pilot will not expect — see
      "Left open".

## 2. The flow
- [x] Users → add `office`, role user, unix via browser terminal (port 7701).
      Saved.
- [x] Files → Network storage → share `work` on `/work`, user `office`.
      Saved; `SERVICE_NAS=on` by itself; `pipeos-nas` running.
- [x] SMB password for `office` set. Saved.
- [ ] **First logon FAILED** — `NT_STATUS_LOGON_FAILURE` from the
      workstation, both `office` and `PIPEOS-A4E0\office`. The hash on the
      box matched the password; `pdbedit -L` listed the user; smbd's log at
      `auth:10` said `pdb_getsampwnam (TDB): error fetching database` — the
      smbd parent held `passdb.tdb (deleted)`: sealing the db re-exported it
      as a new inode under the running daemon. Filed **#268**.
- [x] `rc-service pipeos-nas restart` (what a share change already does):
      list, put, get, rm over SMB3 as `office` — round trip identical.
- [x] The Storage page's "who has an SMB password" list read empty
      throughout: `pdbedit -s /dev/null` reads the wrong private dir (#268).

## 3. Reboot
- [x] `pipeos verify` PASS → reboot → answering in **51 s**, `pipeos-nas`
      started on its own with a live passdb handle, verdict all green.
- [x] put/get/rm over SMB3 again from the workstation: identical. The share
      survives a boot without a hand.

## 4. Take it down
- [x] Storage → shares `[]` → `SERVICE_NAS=off` by itself, selfcheck green,
      `pipeos verify` PASS. Account `office` left in place.

## 5. Left open
- #268: the vault keeps an unchanged file's inode; a password set restarts
  smbd; `pdbedit -s` against the rendered conf. (PR alongside this record.
  Boot ordering was never the problem: pipeos-vault already declares
  `before pipeos-nas`.)
- The unix-access detour in §1: a "share only" account — unix login for
  samba's sake with no shell, no key, no terminal — so the Storage page can
  offer "create an account for this share" in one step. Needs an issue.
- Not exercised: an external drive as the share root (UUID path), a second
  client (macOS/Windows Finder/Explorer), read-only shares, throughput.
